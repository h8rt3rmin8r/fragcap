# Helper and Packet Evidence Contract

An admitted selected flow records `selected`, `proxy-attempt`, and a one-use receipt. Helper completion records its exact stage and elapsed time. Success records `proxy-connected`; failure records a typed reason and the actual I/O kind where applicable. A helper registered before receipt consumption reports `unconsumed` if admission fails; only actual ledger consumption reports `consumed`. A pending first packet lost after owner change or shutdown records both aggregate loss and `selected-packet-disposition: lost`. A selected first packet successfully returned to Windows after helper failure records `selected-packet-disposition: reinjected` and keeps the receipt unconsumed. The new reinjected disposition uses route-event evidence version 3; prior consumed and lost records remain version 2. If that return fails, it records `lost`. Neither state claims passive original-packet presence.

The selected flow carries the exact process stage role proved at admission. A direct executable can be `target`; a launcher chain's final client is `client`. Packet-owner equality uses that role. Helper-facing proxy facts normalize the final game as `client` for exact-game inspection. A matching tuple, digest, and PID with a different stage role cannot establish an observed-owned original.

The managed packet gate normally requires the packet instant inside the ETW causal interval. A native direct-route attestation proves one exact selected first packet and its process generation independently. That first packet may pass before ETW publication if its role is retained and the capture window, direction, and volume bounds allow it. This exception never promotes an ordinary socket-table packet or a same-tuple later packet.

The worker does not wait for SOCKS CONNECT. Its pending state is bounded by exact tuple and endpoint generation. A duplicate selected packet is either retained under the same pending owner or explicitly accounted; it cannot begin a second helper. Session stop closes pending helper work within its finite deadline and retires receipts.

Route reachability requires actual client transfer. Passive original-packet presence is an independent field. Original-absent and incomplete-history states never become original-present because a helper packet or later same-tuple packet was observed.

When the socket-table attributor misses, the capture pipeline may attribute one complete datagram to a selected direct flow only if its full network-datagram digest or a digest omitting only the IPv4 header and TCP/UDP checksum fields, tuple, and capture instant match exactly one route-selected first packet. Checksum normalization accounts for the different capture planes under Windows checksum offload; IP identity, transport header, options, and payload remain in the accepted digest. The managed write gate must still prove the selected process generation and terminal role at that packet instant. The output marks this evidence `attr=direct-route`, never `live`. Missing, truncated, time-mismatched, digest-mismatched, or competing evidence remains unresolved. Capture-side aggregate counts distinguish tuple observations, time mismatches, incomplete packets, digest mismatches, ambiguous matches, exact matches, and checksum-normalized matches without storing raw bytes or digests in diagnostic text. Separate IP-ID-normalized and transport-only comparisons count diagnostic near matches but never grant attribution.

Candidate resolution indexes socket events by tuple so traffic for other sockets does not multiply each held packet's scan cost. A new packet checks only its own proof; held candidates are reexamined when socket or process evidence changes and otherwise expire by deadline in enqueue order. Cleanup records the largest candidate queue delay, the largest held duration, and the count held over 50 ms. These are diagnostic facts; they do not waive the physical unrelated-traffic limit.

The portable package test checks full route journal, compatibility, terminal result, and manifest readback for original-present, original-absent, truncated, refusal, no-payload, reuse, ambiguity, and TCP/UDP cases. A controlled test result does not assert an installed ESO result.
