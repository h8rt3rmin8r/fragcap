---
title: Writing a profile
description: How to author a profile that names a client launched indirectly through a launcher.
---

<Callout title="Why it matters here">
A profile is what turns "capture some traffic" into "capture this game's
traffic, attributed to it." Capture still needs the **npcap** driver; a profile
does not change that, it decides what gets attributed once you capture.
</Callout>

A profile names a game and describes the processes whose traffic fragcap should
attribute to it. The hard case, and the one fragcap exists for, is a client that
you do not start directly: you launch a platform or publisher launcher, and it
starts the game. This guide writes a profile for exactly that shape. For the full
list of keys, see [the profile schema](/docs/reference/profile-schema).

## Start from the identity

Every profile opens with the schema version, the artifact kind and fidelity, and
the game's identity. This is the top of the file; a profile also needs at least
one stage, added next:

```json
{
  "schema": 1,
  "kind": "profile",
  "fidelity": "authored",
  "game": {
    "id": "game-id",
    "name": "Game Name"
  }
}
```

The `id` is a lowercase slug (letters, digits, hyphen, underscore) you pass to
`--profile`. `fragcap steam profile <APP_ID>` prints a starting skeleton like
this for an installed Steam title, which you then edit.

## Name the client stage

A stage is a process fragcap watches for, written as one object in the profile's
`stage` array. The simplest profile has a single client stage, matched by
executable name; that one stage looks like this:

```json
{
  "role": "client",
  "lifecycle": "session",
  "terminal": true,
  "match": { "exe": "<client>.exe" }
}
```

`"terminal": true` means the capture ends when this process exits, and a terminal
stage is always `session` lifecycle. `match` here matches by the executable file
name.

## Disambiguate an indirectly launched client

Matching by `exe` alone is enough when the name is unique. It is not enough when
several processes share an image name, or when you need to be sure you are
capturing the client the launcher started rather than an unrelated copy. That is
what `descends_from` is for: it matches a process whose ancestor is another
stage's process. Assembled with the identity above, the whole profile reads (a
complete document you can validate as-is, once you replace the placeholder
executable names):

```json
{
  "schema": 1,
  "kind": "profile",
  "fidelity": "authored",
  "game": {
    "id": "game-id",
    "name": "Game Name"
  },
  "stage": [
    {
      "role": "launcher",
      "lifecycle": "transient",
      "match": { "exe": "<launcher>.exe" }
    },
    {
      "role": "client",
      "lifecycle": "session",
      "terminal": true,
      "match": { "exe": "<client>.exe", "descends_from": "launcher" }
    }
  ]
}
```

Now the `client` stage matches only when the process descends from the one the
`launcher` stage matched. fragcap resolves `descends_from` over the process
tree it builds from creation-time telemetry; it never opens a handle to the target
and never matches a process against itself.

## Validate before you capture

```text
fragcap profile validate ./<profile>.json
```

Validation runs before every capture anyway, but running it directly reports every
problem in one pass while you are still editing: an unknown key, a stage that
matches nothing, a role named by `descends_from` that no stage declares. Fix all
of them, then capture:

```text
fragcap run --profile ./<profile>.json --out capture.fcapng
```
