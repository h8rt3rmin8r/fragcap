# Research: Installed Direct Route Acceptance

## Decision 1: Treat route transfer, passive packets, and native storage as separate authorities

**Decision**: A positive selected route requires the exact client generation and one-use receipt plus observed client response and two-way proxy bytes. Npcap original-packet availability is reported separately. An installed default-path claim additionally requires exact physical target-store, registry, and bundle readback.

**Rationale**: S203 and S204 already separated these facts. Rejoining them through a single aggregate success flag would recreate #593 and #594. The constitution's installed-product rule rejects custom-path package harnesses as default-storage proof.

**Alternatives considered**: Upstream SOCKS CONNECT as reachability, selected-packet count as client delivery, and a custom test bundle as default placement. Each is insufficient evidence.

## Decision 2: Use one cold controlled client and ephemeral external peer as the acceptance spine

**Decision**: Reuse the S204 finite cloudbase peer and exact byte/sentinel assertions. The S205 package case uses three paired sentinels before route activation, three after an exact selected-client reply while that connection remains open, and three after cleanup; the S204 peer default remains unchanged. Drive the client through candidate package entry points, including an installed MSI invocation when exact preservation and restoration of the existing v0.11.0 installation are established. Record the published v0.11.0 comparison separately.

**Rationale**: The same flow can prove #593 and produce route, proxy, packet, calibration, and cleanup evidence for #594 and #595. Cloudbase is shared; the peer remains unprivileged, creates no remote file or service, and must be verified closed. The workstation currently has published v0.11.0 at C:\Program Files\fragcap\fragcap.exe. Candidate package certification already compares installed MSI and ZIP executable bytes, but its redirected smoke roots cannot prove the workstation default-path journey.

**Alternatives considered**: An unowned public echo endpoint, a permanent cloudbase listener, or treating the elevated Rust probe as installed behavior. None provides the requested exact installed controlled evidence.

## Decision 3: Preserve the published installation before any candidate MSI change

**Decision**: Preflight exact installed MSI product identity, official restoration bytes, installation CA identity, target store, active sessions, and Doctor recovery status. Refuse candidate installation if exact restoration cannot be demonstrated. Use the installed CLI's documented defaults, no storage override, for any default-path claim. A hosted disposable package runner remains useful for candidate package lifecycle but is not evidence of the workstation's effective native paths.

**Rationale**: A same-version candidate MSI may replace existing files or fail Windows Installer source resolution. The installed-product constitution protects native evidence and requires actual canonical paths, not nominal environment variables.

**Alternatives considered**: Uninstalling first without source proof, changing the default store to a scratch location, or substituting a portable binary for installed default-path evidence. All would lose or misstate authority.

## Decision 4: Require observed passive packet order

**Decision**: Use actual Npcap output plus signed-route receipts for original-present and original-absent flows. Start order and host topology may be varied in a controlled environment only after verifying unrelated traffic continuity. If one physical order cannot be produced, keep #594 open and state the exact missing row; synthetic correlation fixtures remain necessary but cannot replace it.

**Rationale**: The initial field defect was an interaction between diversion and passive capture. A route event proves a selection, not that Npcap saw the original packet. S204 did not run both physical orders.

**Alternatives considered**: Inferring driver order from flow counts, using a packet crafted by a fixture, and treating the absence of any passive packet as proof of Npcap order. Each confuses source authority.

## Decision 5: Complete report acceptance through native source fixtures and one installed readback

**Decision**: Extend the existing route-event and CLI bundle fixtures for refusal, writer failure, cleanup partiality, optional capture, source digest preservation, Doctor, manifest, and share transformation. Use one source-of-truth decision for human and JSON summaries. The installed journey inventories actual native artifacts without writing a duplicate agent report into the bundle.

**Rationale**: The S203 implementation already provides a bounded route stream and derived report, but S204 left multiple acceptance rows unchecked. Focused fixtures expose gaps without requiring a private title.

**Alternatives considered**: Duplicating the event stream in a new log, serializing on the broad packet hot path, or copying private route identifiers to a shareable report. These violate existing architecture and authority boundaries.

## Open empirical questions to resolve during implementation

- Whether the current Windows host or a disposable Windows environment can produce both physical Npcap original-packet orders.
- Whether candidate MSI installation can be restored exactly from verified published v0.11.0 bytes without disturbing native state.
- Whether the current default-path target registration and controlled raw-client launch surface can express the cold journey without a new product command.

These are measured task outcomes, not permissions to claim missing evidence as success. No product dependency or release change is planned.
