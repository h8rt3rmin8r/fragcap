# Contract: Dispatch and History

## Before authorization

Resolve the target and its stored association. Prepare the selected launch and any one alternate without effects. The authorization payload names both methods, exact target and scope, launch and route effects, fallback conditions, and whether any process is session-owned. A target or association change invalidates the plan before effects.

## At dispatch

Cold platform creation uses the existing exact root receipt and one title dispatch. Warm platform dispatch uses one query-only verified platform generation and never applies retroactive environment variables. An unassociated game uses the declared direct executable. A game already running or a second plausible generation blocks a duplicate dispatch. Only the exact final-game generation can enter selected routing or retained game payload evidence.

If the cold platform root cannot be created before title dispatch, the single authorized direct alternate may run after a fresh game-image inventory finds no running game. An association that cannot be resolved at preflight refuses before an alternate can be authorized. If dispatch delivery is uncertain, the game exists, or current process state is unavailable, fallback is refused. Every method attempt has a named terminal state. A warm platform and its game receive no process-control operation; the approved plan discloses that the game remains running and existing redirected connections may close when finite routing ends.

## After the attempt

Append one capture history row with selected and observed facts, including failure, partial evidence, and cleanup. History append failure is reported independently and cannot upgrade a partial capture. A subsequent run reads history for advisory drift only. The current authorization never consults history as permission or prerequisite.

## Controlled matrix

Cold Steam, warm Steam, direct unassociated game, unavailable association preflight refusal, publisher handoff, preexisting game, unrelated same-name process, parent PID reuse, two candidate games, platform exit, successful dispatch with no game, one safe fallback after cold root creation failure, and refusal of uncertain fallback are required. First, repeat, failure, target update, scope change, route change, rollback, pruning, migration, append failure, and privacy readback are required history cases. Every case checks no duplicate dispatch, exact route scope, and truthful outcome.
