# Research: Direct Socket Route

## Decision 1: Use the selected signed WinDivert component for packets and socket events

WinDivert NETWORK can block and reinject packets but has no process ID. SOCKET and FLOW expose process ID and endpoints but no payload; FLOW events cannot be blocked. The adapter must observe before managed launch, join an exact socket event to process generation and packet tuple, and retain a bounded unknown state when ordering is insufficient. A SOCKET observer needs both sniff and receive-only: receive-only is mandatory at that layer, but without sniff it blocks matching connect operations. FLOW also requires sniff plus receive-only. WinDivert timestamps use QueryPerformanceCounter, not Unix time: event-to-packet ordering stays in that clock domain, while a bounded sampled conversion is needed only to compare with existing process-generation evidence. The official component packaged by S199 is the only driver dependency. [Upstream layer and timestamp documentation](https://reqrypt.org/windivert-doc.html).

The broad interception alternative, adopted by mitmproxy's redirector, handles all nonloopback traffic and reinjects unselected packets. It shares a user-mode queue with unrelated traffic, so a pass-through latency and loss measurement is required before selection. The original S200 design starts with a PID-bearing SOCKET observer using `WINDIVERT_FLAG_SNIFF | WINDIVERT_FLAG_RECV_ONLY` and opens narrowly filtered packet handles for exact tuples only after owner proof. A missed first packet is an explicit bypass; positive routing requires observing the initial TCP SYN or first UDP datagram through that handle. [Mitmproxy Windows redirector](https://github.com/mitmproxy/mitmproxy_rs/blob/main/mitmproxy-windows/redirector/src/main2.rs).

## Decision 2: Use a bounded local TCP/IP stack at the packet-to-stream boundary

Rewriting a destination to a loopback listener and relying on the Windows stack to accept the modified flow has uncertain local-address and loopback-direction semantics, especially for IPv6 and reply injection. A local stack gives explicit TCP sequence, retransmission, half-close, and UDP datagram ownership, and keeps the native proxy at its existing stream boundary. `smoltcp` 0.12.0 supports IPv4/IPv6 and Rust 1.80, within this workspace's 1.89 floor; it and its `managed` 0.8.0 dependency carry 0BSD. Both require exact reviewed, explicitly approved dependency-license exceptions before inclusion. Newer 0.13 and 0.14 require Rust 1.91. No Python component or mitmproxy API is introduced. [smoltcp release notes](https://github.com/smoltcp-rs/smoltcp/releases), [smoltcp license](https://github.com/smoltcp-rs/smoltcp/blob/main/LICENSE-0BSD.txt).

## Decision 3: Bind original flow separately from helper socket

The native proxy currently looks up the owner of its client-facing socket. Once the local route stack creates a helper leg, that lookup names Fragcap. A session-private one-use receipt ledger must provide the original flow as an alternate typed authority for a bridge-created connection; the helper socket remains separately visible. Missing or consumed receipts cannot become positive game ownership. The implemented bridge negotiates one authenticated SOCKS5 CONNECT for direct TCP and UDP ASSOCIATE for datagrams. After CONNECT, the proxy classifies observed bytes: exact direct-owner HTTP and TLS enter the existing native HTTP/TLS protocol engines, while raw TCP remains in the bounded generic relay. This differs from the issue's suggested HTTP CONNECT framing for TLS but preserves its inspection and trust boundaries without a second helper connection or protocol preselection based on port. A destination port alone never decides inspectability.

## Decision 4: Compare WFP connect redirection

Microsoft's ALE connect-redirection model can select a specific connection and preserve its original destination before packets move, which directly avoids the event-to-packet race. It requires a WFP callout driver that is outside the S199 selected component and package policy. WinDivert remains selected; its race is exposed as a named bypass rather than concealed as successful routing. [Microsoft connect redirection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-bind-or-connect-redirection).

## Open implementation proof

The narrow-handle event timing caused a missed initial SYN in each disposable route probe. The owner-approved broad pass-through changes the positive-route design, but the complete disposable Windows matrix, not the short prearm probe, decides whether the selected adapter meets #581 and #582. If the broad queue, candidate wait, watchdog, or sentinel isolation fails, the S200 gate remains red and the route cannot be offered as complete.

The first [disposable Windows probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42765103032) confirmed a nonblocking SOCKET observer, a completing loopback connection, and event timestamp 4212672243 before SYN timestamp 4212672831 (588 QueryPerformanceCounter ticks). It did not prove that a new exact NETWORK handle can open within that interval. The follow-up probe must divert and reinject the initial SYN after opening its handle in response to the event.

The follow-up [disposable run](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42766510266) confirmed the matching SOCKET event and a subsequently opened narrow NETWORK handle, but that handle never received the initial SYN before the client connected. A final [clean-path run](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42766943875) prepared the filter before the event and removed logging and queue-parameter work from the event-to-open path. It again matched the exact test connection (local port 53623, remote port 53622), opened the handle, and missed the SYN. The pre-armed sniff observer saw event timestamp 3740140492 and SYN timestamp 3740141054 (562 QueryPerformanceCounter ticks). The narrow test was stopped after the connection completed; its pending `WinDivertRecv` returned Windows broken-pipe error 232. This is a failed required positive route row, not a completed S200 route.

WinDivert's NETWORK filter has no process-ID field, while the PID-bearing SOCKET layer cannot replay a blocked connect event. Prearming a broad packet-diversion filter temporarily intercepts unrelated first packets before process proof; the owner explicitly approved this bounded pass-through and constitution 3.0.0 records it. Header-only candidacy is permitted, but unrelated application payload cannot be inspected or retained. A WFP ALE connect-redirection callout can decide at the connection boundary but changes the selected signed-driver architecture. The bridge and driver-free model remain useful, but implementation cannot claim #581 or #582 until the full live route and isolation matrix passes.

Microsoft's ALE layer is the only WFP layer that can filter by application identity; its connect-redirection callout can change one connection's destination before packets are sent and pass the original destination to the local proxy. This resolves the observed event-to-packet race in principle, but it requires a new kernel-mode callout driver, a separate signing and distribution path, and an amendment to P-1's exact WinDivert-only technique boundary. The existing signed WinDivert component does not supply that callout. On 2026-11-10 the owner selected a brief, bounded global WinDivert pass-through after reviewing measured delay. Constitution 3.0.0 now permits unrelated TCP/UDP packets to enter a finite pass-through only for prompt reinjection; selected game routing still requires exact client and original-destination proof. [Microsoft ALE application identity](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-), [connect redirection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-bind-or-connect-redirection), [kernel-mode driver signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/driver-signing).

The first [broad pass-through probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42768209914) measured 200 paired loopback UDP exchanges: before p99 41 microseconds, during p99 122 microseconds, after p99 57 microseconds, with all 400 packets reinjected and no missing replies. The [prearmed first-SYN probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42768592354) caught and reinjected the initial TCP SYN; before p99 128 microseconds and during p99 200 microseconds for the paired local UDP exchange. The [parallel probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42768868563) again caught the first SYN; paired serial p99 moved from 172 to 243 microseconds, while four parallel local conversations over 2,000 exchanges had 520-microsecond p99 and 926-microsecond maximum round trip. All 4,400 received packets were reinjected and no tested reply was missing. These were short disposable-runner observations, not a sustained-load or stalled-worker guarantee. Both later workflow runs were intentionally cancelled after their probe steps passed; the full route matrix and exact-head CI remain pending.

The narrower user-mode WFP management API can configure built-in permit/block filters, but Microsoft's redirect API explicitly requires a kernel-mode companion callout; the proxy-side socket controls do not replace it. Thus there is no documented user-mode-only ALE pause or redirect path that preserves this slice's exact target and original-destination requirements. [Microsoft callout design guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/callout-driver-programming-considerations), [proxy redirect socket control](https://learn.microsoft.com/en-us/windows/win32/winsock/sio-set-wfp-connection-redirect-records).

The [first live packet-to-stream probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42771212235) caught the initial SYN but timed out because smoltcp rejected the diverted loopback IPv4 header. The [diagnostic run](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42771932519) found a software-invalid IPv4 header checksum on the diverted packet while its TCP checksum verified and WinDivert's `IPChecksum` flag was set. The [corrected live probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42772266976) normalized the private stack's IPv4 checksum view and exchanged exact `stack-in` and `stack-out` bytes without an OS listener accepting the connection. The [narrower verified-boundary rerun](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42772723207) passed all four disposable probes: only packets WinDivert marks IP-checksum-valid can receive that normalization, and an unfinished checksum without the flag is refused in the driver-free test. The workflow was deliberately cancelled after its probe step passed because the full S200 route is still incomplete. This proves loopback first-packet termination, not the proxy bridge, real external destinations, UDP, failure watchdog, or full matrix.

A separate driver-free test now connects the finite packet stack to the actual native proxy through one session-authenticated SOCKS5 helper, sends a raw request to the exact original TCP destination, half-closes, and receives the exact reply. It checks the proxy's successful CONNECT and directional byte counts. This proves the mechanical stack-to-proxy bridge without WinDivert, but it does not yet bind an original process receipt into proxy correlation or run a full managed chain through the Windows driver.

The [socket-tuple and QPC probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42774537735) decoded the PID-bearing SOCKET event's IPv4-mapped address words, matched its full local and remote tuple to the actual first SYN, and sampled a bounded QPC-to-FILETIME anchor with 100,400 ns declared error in that run. The observer and packet events remained ordered in the common QPC domain. This supports exact event matching; the production observer, candidate wait, and process-generation join still require end-to-end verification.

The [bounded passive observer probe](https://github.com/h8rt3rmin8r/fragcap/actions/runs/42775007486) started the actual all-TCP/UDP CONNECT observer before a synthetic connection, retained its exact PID, endpoint ID and tuple, and reported 100,250 ns QPC conversion uncertainty with no capacity loss. The five disposable probe tests passed before the workflow was intentionally cancelled; the candidate queue and route worker remain unimplemented at this checkpoint.

## Decision 5: Report the WinDivert driver queue limit

The owner approved keeping WinDivert with explicit uncertainty. WinDivert can lose packets in its kernel queue before `WinDivertRecv` returns them and provides no exact pre-receive drop counter. Adapter accounting is therefore exact only for delivered packets. The product must surface the pre-receive count as unmeasurable, and the controlled original-flow oracle plus active sentinels must show zero observed missing replies or unexplained loss. This is a documented change to FR-006 and SC-003, not a proof that no kernel-queue drop occurred.
