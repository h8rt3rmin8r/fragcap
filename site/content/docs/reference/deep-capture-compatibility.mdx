<Callout title="Functional, not feature-complete">
This matrix describes the S105 native HTTP/1.1, HTTP/2, CONNECT, HTTPS,
metadata, bounded body, and live application-stream path.
[Issue #278](https://github.com/h8rt3rmin8r/fragcap/issues/278)
owns the remaining protocol, launch, artifact, recovery, and packaging work.
</Callout>

<Callout title="The short version">
**Capture** passively records packets and process attribution. **Deep Capture**
runs Capture alongside an explicit, target-scoped local proxy. Deep Capture can
add HTTP semantics only when the selected software actually routes traffic
through that proxy and accepts the fragcap-owned local certificate authority.
</Callout>

Rust integrations can drive the same behavior through `fragcap::deep_capture`.
The public API supports side-effect-free preflight, exact-plan authorization,
checked lifecycle methods, narrow proxy, trust, launch, Capture, and storage
adapters, typed events, and one authoritative terminal report. Controlled
adapters require no capture driver, elevation, game account, remote service, or
trust-store change.

Deep Capture does not promise that every encrypted flow becomes readable. It
does not bypass certificate pinning, downgrade TLS, extract keys from a target
process, or silently change system-wide proxy settings. Packet truth remains
available through Capture even when application inspection is unavailable.

See [Output formats and session bundles](/docs/reference/output-formats) for the current v0.8 artifact authority, sensitivity, omission, correlation, retention, and cleanup contract. Native manifest, HAR, correlation, and proxy/cleanup sidecar completion is owned by [#335](https://github.com/h8rt3rmin8r/fragcap/issues/335), [#302](https://github.com/h8rt3rmin8r/fragcap/issues/302), [#303](https://github.com/h8rt3rmin8r/fragcap/issues/303), and [#336](https://github.com/h8rt3rmin8r/fragcap/issues/336).

## Traffic support

| Traffic | Capture | Deep Capture | Outputs and limits |
| --- | --- | --- | --- |
| HTTP | Records packets, attribution, and payload bytes unless `--no-payload` is selected. | Observes HTTP/1.1 metadata and bounded streaming bodies when the request reaches the proxy. | HTTP/2 cleartext prior knowledge is limited to explicitly routed authorized traffic; WebSocket and event-stream semantics remain deferred. |
| HTTPS | Records encrypted packets and attribution. | Negotiates native HTTP/1.1 or HTTP/2 after the connection reaches the proxy and accepts the local CA, retaining available metadata and bounded body evidence. Explicit paired operator-owned credentials support upstream mutual TLS. | Certificate pinning is classified only when conclusive and is never bypassed. Ambiguous refusal remains unknown. |
| WebSocket | Records packets and attribution. | Can observe the HTTP upgrade handshake when it reaches the HTTP proxy. | Complete frame and message support is [#295](https://github.com/h8rt3rmin8r/fragcap/issues/295). An observed handshake is not full support. |
| Non-HTTP TLS | Records encrypted packets and attribution. | Records proxy connection metadata when the flow reaches the proxy, without interpreting the application protocol. | Generic native stream observations are [#312](https://github.com/h8rt3rmin8r/fragcap/issues/312); protocol-specific interpretation remains an explicit dissector or omission. |
| QUIC | Records the underlying UDP packets and attribution. | Unsupported by the current HTTP proxy path. | Scoped QUIC and HTTP/3 are [#314](https://github.com/h8rt3rmin8r/fragcap/issues/314). No current routing or decryption claim. |
| UDP | Records packets, attribution, and payload bytes unless `--no-payload` is selected. | Unsupported by the current proxy path. | Generic native UDP relay is [#313](https://github.com/h8rt3rmin8r/fragcap/issues/313). Packet truth remains available. |
| Plaintext | Records packets, attribution, and payload bytes unless `--no-payload` is selected. | Plaintext HTTP follows the HTTP row. Other plaintext protocols have no generic application dissector. | Generic stream records are [#312](https://github.com/h8rt3rmin8r/fragcap/issues/312); exhaustive omissions are [#316](https://github.com/h8rt3rmin8r/fragcap/issues/316). |

In compatibility facts, `full` means the proxy observed supported HTTP semantics for that
run. It does not mean that every body byte, WebSocket frame, or custom payload
was retained. Bounded retention and explicit omission or truncation remain
authoritative. A TLS key log is an analyzer aid produced by the proxy
side of the session. It is not a key extracted from the selected process.

## Local target matrix

Compatibility depends on the launch path and local evidence. fragcap therefore
does not publish a guessed title list. Inspect the facts stored for one selected
target instead:

```text
fragcap targets show sample-target
```

With evidence, the detail view adds one line per stored fact:

```text
compatibility:
  proxy-routing = reached-client | launch=steam-protocol-cold | source=observed-run | freshness=current
  inspectability = metadata-only | source=stale-observation | freshness=stale
```

Without evidence, it says:

```text
compatibility:  unknown (no stored evidence)
```

Repeated or conflicting rows remain visible. fragcap does not collapse them
into a single compatible or incompatible verdict because two launch cases,
target versions, or proxy backends can produce different results.

## Evidence and freshness

| Label | Meaning |
| --- | --- |
| `observed-run` | fragcap recorded the fact during an authorized run. |
| `user-confirmed` | An operator explicitly confirmed the fact. |
| `imported-catalog` | The fact came from an external catalog source. Import provenance does not by itself make the fact current or stale. |
| `stale-observation` | Historical context that always appears as stale. |
| `current` | The row is not marked stale and is not a stale observation. |
| `stale` | The row is marked stale or has the `stale-observation` source. |
| `unknown` | A successful local-store read found no compatibility facts. No result was inferred from the title, engine, platform, or executable. |

`targets show` is read-only. It does not launch software, start a proxy, change
certificate trust, contact a catalog, or refresh facts. A later explicit and
authorized Deep Capture measurement can add newer evidence. Existing
launch-specific rows remain available as context rather than being silently
rewritten.

## Calibrating an unknown target

Compatibility calibration is the supported, explicit path from unknown local evidence toward ordinary Deep Capture eligibility. It keeps the ordinary safety gate intact and measures one declared launch case in two separate runs.

First close the selected target and, for a Steam launch, close Steam. Then measure scoped proxy reachability without changing certificate trust. This example uses the Steam launch case:

```powershell
fragcap deep-capture sample-target --launch --calibrate reachability --launch-case steam-protocol-cold
```

For an eligible stored direct target, use `--launch-case direct-exe-cold` instead. Warm Steam and direct-executable targets are refused before side effects.

fragcap displays the target, phase, launch case, loopback proxy action, bundle destination, finite deadlines, possible fact writes, and cleanup obligations before asking for confirmation. A shorter `--wait` or `--duration` becomes the displayed calibration bound; longer values are capped at the calibration maximum. Shutdown and cleanup enforce the displayed bounds too. `--yes` preconfirms that displayed plan for an unattended run. JSON mode requires `--yes` because it cannot mix a prompt into the event stream.

Review the new rows with `fragcap targets show sample-target`. If current evidence for the same launch case says `proxy-routing = reached-client`, a separate TLS phase can measure CA acceptance and inspectability:

```powershell
fragcap deep-capture sample-target --launch --calibrate tls --launch-case steam-protocol-cold --trust-ca
```

Use the same exact cold launch case in both phases.

Routing and environment propagation remain separate facts. Reaching the final client does not prove how the launcher propagated proxy configuration, and fragcap records `proxy-propagation = confirmed` only when a separate non-invasive observation supports it. CA acceptance requires full HTTPS semantics correlated to the final client, so launcher traffic cannot establish the target's trust behavior. Silence remains inconclusive. A phase outcome such as proxy not reached, metadata only, or unsupported protocol is recorded in the local bundle and is not converted into an aggregate compatible or incompatible target verdict.

## Publishing compatibility evidence

Public documentation and committed fixtures use placeholders such as
`sample-target` and `sample.exe`. Do not publish local title names, account
identifiers, access tokens, filesystem paths, private endpoints, host
identifiers, or unreviewed free-form notes collected during compatibility work.
