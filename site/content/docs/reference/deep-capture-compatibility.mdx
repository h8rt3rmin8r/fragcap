<Callout title="Native implementation and bounded compatibility">
This matrix describes native protocols, final-package certification, stable API and guided calibration shipped in v0.10.0 on 2026-09-15 and retained by v0.10.6. Controlled conformance and packaging evidence are not a universal title-compatibility claim. File a concrete defect against the affected active release when an observed title or environment contradicts this matrix.
</Callout>

<Callout title="The short version">
**Capture** passively records packets and process attribution. **Deep Capture**
runs Capture alongside an explicit, target-scoped local proxy. Deep Capture can
add application semantics only when the selected software actually routes
traffic through that proxy and satisfies the protocol-specific trust and scope
requirements.
</Callout>

Rust integrations can drive the same behavior through `fragcap::deep_capture`.
The public API supports side-effect-free preflight, exact-plan authorization,
checked lifecycle methods, narrow proxy, trust, launch, Capture, and storage
adapters, typed events, and one authoritative terminal report. Controlled
adapters require no capture driver, elevation, game account, remote service, or
trust-store change.

Deep Capture does not promise that every encrypted flow becomes readable. It
does not bypass certificate pinning, downgrade TLS, extract keys from a target
process, or silently change system-wide proxy settings. Packet truth remains
available through Capture even when application inspection is unavailable.

See [Output formats and session bundles](/docs/reference/output-formats) for the
current native artifact authority, sensitivity, omission, correlation, retention,
and cleanup contract. The native bundle includes versioned application and
cleanup streams, packet-to-application correlation, a bounded HAR projection,
and a manifest that declares finalization, completeness, loss, sensitivity, and
omissions for every expected artifact.

## Traffic support

| Traffic | Capture | Deep Capture | Outputs and limits |
| --- | --- | --- | --- |
| HTTP | Records packets, attribution, and payload bytes unless `--no-payload` is selected. | Observes HTTP/1.1 and HTTP/2 metadata, streams, bounded bodies, WebSocket frames and messages, Server-Sent Events, and bounded gRPC envelopes. | gRPC payloads remain opaque. Retained raw payloads may be decoded separately with external schema-aware tooling. Retention and derivation loss stay explicit and do not delay forwarding. |
| HTTPS | Records encrypted packets and attribution. | Negotiates native HTTP/1.1 or HTTP/2 after the connection reaches the proxy and accepts the session CA, retaining available metadata and bounded application evidence. Explicit paired operator-owned credentials support upstream mutual TLS. | Certificate pinning is classified only when conclusive and is never bypassed. Trust, client-auth, and protocol failures never silently downgrade. |
| WebSocket | Records packets and attribution. | Observes verified HTTP/1.1 upgrades and HTTP/2 extended CONNECT, preserving raw frames and bounded derived messages. | Masking, fragmentation, UTF-8, and negotiated per-message compression outcomes are retained. Raw frames remain authoritative. |
| Non-HTTP TLS | Records encrypted packets and attribution. | Authenticated SOCKS5 CONNECT retains opaque encrypted chunks. Trusted no-ALPN HTTP CONNECT can retain bounded decrypted chunks only after both client-facing session-CA TLS and independently verified upstream TLS succeed. | Generic chunks remain protocol-unknown, not custom application semantics. Failed inspection trust or protocol boundaries never fall back silently to transparent forwarding. |
| QUIC and HTTP/3 | Records the underlying UDP packets and attribution. | An authenticated target-owned UDP route can terminate paired QUIC connections and retain bounded HTTP/3 request, response, stream, body, datagram, timing, refusal, and loss evidence. | Exact `h3` ALPN is required. Zero round-trip application data, active migration, changed endpoints, failed trust, pinning, and unscopable traffic are refused. |
| UDP | Records packets, attribution, and payload bytes unless `--no-payload` is selected. | Authenticated SOCKS5 UDP associations support IPv4, IPv6, and proxy-resolved destinations, with bounded generic datagram evidence. | One control connection owns one finite association. Fragmented, spoofed, unsolicited, saturated, oversized, failed, timed-out, and cancelled traffic is counted. Unrouted UDP remains packet-only. |
| Plaintext TCP | Records packets, attribution, and payload bytes unless `--no-payload` is selected. | Plaintext HTTP follows the HTTP row. Authenticated SOCKS5 CONNECT retains bounded directional chunks for other streams. | Generic records preserve bytes and direction without inventing protocol semantics. |

All supported routes preserve IPv4 or IPv6 family from authorization through
listener ownership, routing, lifecycle, artifacts, and cleanup. The default is
IPv4; IPv6 selection is explicit and never uses a wildcard listener.

In compatibility facts, `full` means the proxy observed the required supported
semantics for that exact target, launch case, route, address family, protocol,
backend, and product version. It does not mean every body byte, WebSocket frame,
or custom payload was retained. Bounded retention and explicit omission or
truncation remain authoritative. A TLS key log is an analyzer aid produced by
the proxy side of the session. It is not a key extracted from the selected
process.

## Local target matrix

Compatibility depends on the launch path and local evidence. fragcap therefore
does not publish a guessed title list. Inspect the facts stored for one selected
target instead:

```text
fragcap targets show sample-target
```

With evidence, the detail view adds one line per stored fact:

```text
compatibility proxy-routing:     reached-client | launch=steam-protocol-cold | source=observed-run | freshness=current
compatibility inspectability:    metadata-only | source=stale-observation | freshness=stale
```

Without evidence, it says:

```text
compatibility:    unknown (no stored evidence)
```

Repeated or conflicting rows remain visible. fragcap does not collapse them
into a single compatible or incompatible verdict because two launch cases,
target versions, or proxy backends can produce different results.

## Evidence and freshness

| Label | Meaning |
| --- | --- |
| `observed-run` | fragcap recorded the fact during an authorized run. |
| `user-confirmed` | An operator explicitly confirmed the fact. |
| `imported-catalog` | The fact came from an external catalog source. Import provenance does not by itself make the fact current or stale. |
| `stale-observation` | Historical context that always appears as stale. |
| `current` | The displayed row is not marked stale and is not a stale observation. This display label alone does not establish applicability to a newly prepared exact case. |
| `stale` | The row is marked stale or has the `stale-observation` source. |
| `unknown` | A successful local-store read found no compatibility facts. No result was inferred from the title, engine, platform, or executable. |

`targets show` is read-only. It does not launch software, start a proxy, change
certificate trust, contact a catalog, or refresh facts. A later explicit and
authorized Deep Capture measurement can add newer evidence. Existing
launch-specific rows remain available as context rather than being silently
rewritten.

## Calibrating an unknown target

Start with the guided front door:

```powershell
fragcap calibrate sample-target
fragcap calibrate --id 42 --protocol https
```

Stored resolution takes precedence. On a clean miss, an exact installed Steam application identifier or case-insensitive display name can produce a separately confirmed registration plan. For a Steam target without an authored client, appinfo supplies a launch hint only. Interactive setup can separately confirm a cold Steam launch and observe owned descendants with operating-system socket rows. One complete observed socket owner can be proposed under an exact client-authoring plan; this does not prove packet traffic or proxy reachability. No owner, multiple owners, incomplete observation, or a decline changes no target row. `--client-executable sample.exe` is an explicitly labeled manual declaration when observation is unavailable. Setup ends after the target change; close the title and Steam normally before rerunning calibration for reachability. A content-derived `--candidate` identity selects one current discovery candidate, never a list position. Registration, setup, and each later session require separate fresh authorization; a choice is not consent to traffic inspection.

The workflow proposes reachability first when applicable routing evidence is missing. Fresh eligible final-client observations can propose concrete protocols, but requested `--protocol` values are only measurement intent. Each workflow runs reachability at most once and each concrete protocol at most once, with at most fourteen durable attempt ordinals. A failure, limitation, decline, partial result, interruption, target change, or repeated case checkpoints coverage and stops later effects instead of pretending success.

Resume from the same effective local store using the workflow identity printed by the command:

```powershell
fragcap calibrate --resume 17 --local-db C:\Users\you\local.db
fragcap calibrate --resume 17 --pause-for login --local-db C:\Users\you\local.db
```

The workflow stores an immutable target snapshot and exact-case intent. Resume rebuilds process inventory, fact applicability, proposal, recovery, bundle, plan, and confirmation authority; it never reuses an old plan or response. An in-flight record first becomes an effect-free interruption pause. Login, EULA, update, anti-cheat, gameplay, shutdown, and interruption pauses record operator work, not compatibility proof. Advanced fresh workflows can assert the inferred cold launch case, choose IPv4 or IPv6, and select child-environment routing; other routing strategies remain pre-effect refusals. Resume cannot change those dimensions or the candidate.

If a delegated session fails, the terminal diagnosis names the earliest known stage from retained launch, process, route, fact, and cleanup evidence. An artifact marked written can contain zero retained target packets. A paused failed workflow retains its attempt history, so `--resume` does not automatically retry that failed exact case. Review the cause, correct it, and start a new workflow with the target selector when another measurement is appropriate. A zero-observation attempt may append a launch-case fact while appending no proxy-routing fact; inspect the exact fact-write report.

Ordinary eligibility uses the latest exact applicable routing row for target/version, launch case, route, loopback family, selected measurement, native backend/version, and fragcap version. A historical `current` display label, imported fact, protocol fact, launcher observation, or another workflow cannot substitute for that decision. See the [CLI reference](/docs/reference/cli#calibrate) for full options.

### Reading a calibration result

The next-source S168 contract presents authorization, observation, captured evidence, resource cleanup, and one final calibration verdict as separate blocks. The complete canonical plan and exact identifier still govern authorization. Human field anchors use the widest actual label plus four spaces; redirected output is plain, quiet suppresses ordinary guided progress and its final human verdict, silent suppresses terminal evidence, and JSON carries additive `calibration.verdict` decisions instead of prose. Required authorization and actionable cleanup notices retain their established visibility.

The final verdict separates the attempted case from current applicable stored readiness. Its case identity includes target, launch, route, address family, native backend/version, fragcap version, target version when available, and protocol. The greatest durable row ID for each exact applicable measurement key supplies current readiness; older differing values remain history. A later exact negative measurement supersedes an earlier positive one, and a later exact positive measurement supersedes an earlier negative one. A stale or unrelated attempt does not displace an applicable current measurement. Contradictory values at the same greatest durable ID, or absent durable chronology, cannot establish readiness. A satisfied stored routing prerequisite still requires fresh launch preflight, recovery, and authorization. Remaining protocols are explicit. Resume preserves workflow intent and attempt history and obtains a new plan; one supported next command is printed with that purpose.

Connection endings and application exchanges count different populations. For example, a controlled session can report six failed connections, with five protocol failures and one idle timeout, while seven HTTP exchanges completed successfully. The timeout does not erase those exchanges. Separate fields show accepted/completed/failed/forced/live connections, retained failure categories, exchange/stream totals, bounded detail loss, record ownership, and unavailable correlation. Records observed during the observation window and later owner release remain distinguishable. Later records are retained but cannot satisfy the earlier calibration case.

A finished session can have partial process evidence and readable written artifacts without proving selected-client reachability. The terminal evidence block reports manifest and process-trace completeness and exact available limitation counts independently from session finalization, writes, recipient-context access, fact writes, and cleanup. It prints the bundle root once and relative artifact names, and gives an omission reason instead of claiming an unrequested file exists. The S170 correction published in v0.10.6 verifies ordinary recipient access after writer and lifecycle reconciliation and withholds accessible analyzer-opening guidance when that verification fails. Published v0.10.6 includes this correction.

### Ordinary desktop access and historical repair

Same-account administrative capture retains the intended user's exact SID and ordinary access context. Private output grants that recipient, any distinct producer and SYSTEM explicitly, covering inherited files, atomic publication and independently protected sidecars. Administrator-group ownership and a successful elevated read do not establish ordinary access. Readable evidence can still be partial or fail to prove final-client reachability.

Elevation under different credentials requires an explicit `--output-recipient <SID>` and exact `--bundle <PATH>`. The waiting command emits a quoted `bundle access-authorize` helper command for the intended ordinary terminal. Run that exact helper within sixty seconds, then review the full session authorization plan. An unknown recipient, elevated helper, changed request or mismatched destination refuses before session output or effects. No arbitrary desktop account is guessed.

For an existing inaccessible bundle, run the [read-only inspection and exact permission repair commands](/docs/reference/cli#bundle-access-inspect) from a console that can read its provenance and apply the proposed permissions:

```powershell
fragcap bundle access-inspect 'C:\captures\fragcap-session'
fragcap bundle access-repair 'C:\captures\fragcap-session' --authorize '<INSPECTION_ID>'
```

Review the inspection and substitute its exact identifier. Repair requires a recognized terminal manifest, matching closed resource journal and inactive ownership where a generation-qualified owner record exists. Active or unknown matched ownership, unreadable authority, unknown files, reparses, outside hard links and changed previews refuse. Independently protected `.sensitive-actions.jsonl`, `cleanup.jsonl`, `proxy.jsonl` and `resource-journal.jsonl` are included. Proven owned output containers receive narrow non-propagating enumeration/traversal grants; arbitrary profile/custom ancestors remain unchanged. Final actual-access results and per-path failures are reported outside retained evidence. Content bytes, retention obligations and empty containers are preserved; no collection, purge or trust/proxy recovery is implied.

### Session retention and collection

The S171 correction published in v0.10.6 declares finite retention for newly generated Deep Capture and calibration history: 30 days from terminal manifest publication, 20 completed managed sessions and 2 GiB of eligible logical contents. Oldest eligible contents are collected first after an authorized effectful session finishes, excluding its returned bundle. The exact authorization and terminal presentation show the selected policy. Choose `--retain-bundle` to save generated evidence until explicit cleanup; explicit `--bundle` destinations and their guided attempt siblings are always retained. Historical bundles keep their previous promise. This retention policy ships in v0.10.6.

Use [bundle collect](/docs/reference/cli#bundle-collect) to preview and authorize existing backlog reclamation. Include retained evidence only by selecting `--include-retained`; select custom output with `--bundle`. Collection validates whole-session ownership, inactive generation leases, closed manifest/journal provenance, complete recognized files and every recovery obligation. Active, malformed, unknown, unsupported, unreadable, reparse and replaced populations remain unresolved with their authority preserved. Collection never performs trust recovery.

New ownership leases are visible across Windows desktop sessions. Historical session-local ownership remains unresolved when the original process may still exist and its generation cannot be conclusively checked. The refusal preserves that bundle and reports the missing authority.

Routine collection preserves empty session container directories. Only separately explicit `--purge-empty` can remove proven eligible exact empty containers. Durable retirement records outside the removed contents support interrupted retries and recognize collected emptiness in read-only Doctor. Results count actual removed logical bytes, not presumed physical disk savings. Exact destructive collection requires Windows; portable inspection does not claim portable deletion. Owner AppData and real trust state are not mutated by controlled acceptance tests.

Byte and file totals describe collected bundle contents. Owner-registry metadata retirement is reported separately; external retirement metadata remains available for exact retry and empty-container recognition.

Controlled Windows tests use synthetic bundles, actual ordinary reads and explicitly labeled group-denied or unrelated-access equivalents. They compare complete fixture bytes, last-write times and sibling permissions and prove truthful denied/partial outcomes. No real game, owner-sensitive bundle, actual elevated Administrators-owned fixture or second human account was exercised. Universal field behavior and a separate release are not claimed.

Current source S169 corrects required loopback acquisition, exact listener filter continuity and stage-bound TCP endpoint orientation under #468. When accepted proxy traffic still lacks eligible final-client correlation, the result remains inconclusive. Closed reason counts distinguish absent flows, withheld or bounded history, acquisition-buffer gaps, outside-window packets and unresolved/conflicting ownership over retained observation-window records. The supported next action is `fragcap doctor` to inspect Npcap loopback readiness, followed by retained evidence inspection; this does not prove ownership or authorize a new measurement. Gameplay retry is not a known remedy. The route-owner action remains visible with its finite normal-shutdown deadline while the proxy is active. Successful cleanup establishes resource release only. Controlled real socket endpoints and synthesized packet frames prove the source contracts; no live driver or real-game compatibility is claimed.

```text
Observed case evidence

Connections completed:         0
Connections failed:            6
HTTP/1 exchanges completed:    7

Cause timeout:                 1

Attempt reason:                  final-client-correlation-missing

```

This abbreviated synthetic example retains the four-space gap after the longest actual label in each block. Full reports additionally expose the exact case, independent artifact/process/cleanup fields, remaining work, and reason codes.

### Advanced single-phase measurements

Compatibility calibration is the supported, explicit path from unknown local evidence toward ordinary Deep Capture eligibility. It keeps the ordinary safety gate intact and measures one declared launch case in two separate runs.

First close the selected target and, for a Steam launch, close Steam. Calibration
requires a cold target and cannot use the ordinary Deep Capture warm
close-and-retry option. Managed direct, cold Steam platform, and declared
publisher-launcher chains are supported. Then measure scoped proxy reachability
without changing certificate trust. This example uses the Steam launch case:

```powershell
fragcap deep-capture sample-target --launch --calibrate reachability --calibration-protocol routing --launch-case steam-protocol-cold
```

For an eligible stored direct target, use `--launch-case direct-exe-cold` instead. Warm Steam and direct-executable targets are refused before side effects.

fragcap displays the exact target and launch authority, phase, loopback and routing policy, process-local CA identity when trust is needed, bundle and sensitive artifacts, finite deadlines, possible fact writes, cleanup obligations, refusal boundaries, and versioned plan identifier before asking once for confirmation. A shorter `--wait` or `--duration` becomes the displayed calibration bound; longer values are capped at the calibration maximum. Shutdown and cleanup enforce the displayed bounds too. JSON and prompt-free automation require `--authorize-stdin`; the caller reads the plan event and returns its exact identifier plus one LF in the same process.

Review the new rows with `fragcap targets show sample-target`. If current evidence for the same launch case says `proxy-routing = reached-client`, a separate TLS phase can measure CA acceptance and inspectability:

```powershell
fragcap deep-capture sample-target --launch --calibrate tls --calibration-protocol https --launch-case steam-protocol-cold
```

Use the same exact cold launch case in both phases.

Routing and environment propagation remain separate facts. Reaching the final client does not prove how the launcher propagated proxy configuration, and fragcap records `proxy-propagation = confirmed` only when a separate non-invasive observation supports it. CA acceptance requires full HTTPS semantics correlated to the final client, so launcher traffic cannot establish the target's trust behavior. Silence remains inconclusive. A phase outcome such as proxy not reached, metadata only, or unsupported protocol is recorded in the local bundle and is not converted into an aggregate compatible or incompatible target verdict.

## Publishing compatibility evidence

Public documentation and committed fixtures use placeholders such as
`sample-target` and `sample.exe`. Do not publish local title names, account
identifiers, access tokens, filesystem paths, private endpoints, host
identifiers, or unreviewed free-form notes collected during compatibility work.
