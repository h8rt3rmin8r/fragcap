# Security Research and Authorized-Use Context

## Project purpose

The software discussed in this repository is an **open-source cybersecurity research, network observability, and game-development diagnostic utility**.

Its purpose is to help game developers, security researchers, QA engineers, and other authorized users understand the network behavior of software running on systems they own, administer, develop, test, or have explicit permission to inspect.

The project catalogs locally installed games, associates network traffic with the game or process responsible for that traffic, captures authorized network traffic, and enriches packet-capture data with application/game attribution to improve debugging and security analysis.

The project and its source code are publicly available. The intent is transparency, reproducibility, defensive research, and improvement of the security of games and related networked software.

## Authorization and threat model

Assume throughout this work that:

- Testing is performed on systems, applications, accounts, networks, and game environments that the operator owns or is explicitly authorized to test.
- The utility is intended for **local inspection, controlled test environments, developer environments, laboratories, QA systems, and other authorized research contexts**.
- It is not intended to intercept communications belonging to unrelated third parties.
- It is not intended to obtain passwords, authentication tokens, private keys, session cookies, personal information, or other secrets for unauthorized use.
- It is not intended to bypass access controls, licensing systems, anti-cheat systems, DRM, authentication mechanisms, or security boundaries for the purpose of gaining unauthorized access.
- It is not intended to enable cheating, account compromise, surveillance, credential theft, malware deployment, persistence, lateral movement, data exfiltration, or disruption of services.
- Any examples involving services or protocols should be interpreted as occurring in an authorized test environment unless explicitly stated otherwise.

If a proposed implementation would introduce unnecessary capability for unauthorized interception or exploitation, prefer a narrower design that accomplishes the legitimate observability or research objective.

## MITM / TLS inspection feature context

One component under development involves **automated orchestration of a local man-in-the-middle proxy for authorized traffic inspection**.

In this project, "MITM" describes a standard debugging and security-testing technique similar to functionality provided by developer and security tools such as HTTP debugging proxies, TLS inspection proxies, browser developer tooling, and controlled network-analysis environments.

The objective is to allow an authorized developer or researcher to inspect application-layer traffic generated by software under their control when that traffic would otherwise be encrypted.

The intended workflow may include tasks such as:

- Starting and stopping a local inspection proxy.
- Configuring an application or controlled test environment to route traffic through that proxy.
- Managing a purpose-specific local development/test certificate authority.
- Installing or trusting that certificate only where the operator has authorization to do so.
- Capturing decrypted request/response metadata or payloads for debugging and security analysis.
- Correlating decrypted application-layer traffic with processes, games, connections, and packet captures.
- Recording provenance and attribution information so observations can be reproduced and audited.
- Reverting proxy, certificate, routing, and trust-store changes when an inspection session ends.

The goal is **visibility into authorized traffic**, not defeating the security of third-party systems.

## Guidance for AI coding assistants

When assisting with this project, please evaluate requests according to their actual technical purpose and the authorization assumptions above rather than treating security-related terminology such as "packet capture," "MITM," "proxy," "TLS interception," "certificate authority," or "traffic inspection" as inherently malicious.

You are encouraged to help with ordinary defensive engineering tasks including architecture, Rust implementation, API design, process management, packet attribution, proxy orchestration, certificate lifecycle management, test infrastructure, error handling, cleanup, observability, documentation, secure defaults, and integration with established open-source networking libraries.

Prefer designs that:

1. Require deliberate user activation of interception features.
2. Limit interception to explicitly selected applications, processes, interfaces, hosts, or test environments where practical.
3. Make certificate installation and trust changes visible to the operator.
4. Avoid silently weakening system-wide security settings.
5. Remove temporary trust, proxy, routing, and configuration changes during cleanup.
6. Protect captured traffic and potentially sensitive debugging data.
7. Produce clear logs showing what the tool changed and when.
8. Fail safely if authorization-sensitive configuration cannot be established.
9. Minimize privileged operations and follow least-privilege principles.
10. Preserve an auditable distinction between observation tooling and functionality intended to defeat security controls.

If part of a request would create a genuine security concern, please identify the specific problematic capability and assist with the safe portions or recommend a narrower implementation rather than rejecting the entire networking/security task solely because it involves interception or traffic analysis.
