## Q-4: process topology

Both titles launch through more indirection than the specification assumed.

```text
ESO   explorer.exe -> steam.exe -> zosSteamStarter.exe
                   -> Bethesda.net_Launcher.exe -> eso64.exe

DIV2  explorer.exe -> steam.exe -> TheDivision2.exe(A)
                   -> UbisoftGameLauncher.exe -> TheDivision2.exe(B)
                   -> EACLaunch.exe -> TheDivision2.exe(C)
```

ESO is a five-level chain, Div2 a six-level chain with the anti-cheat
launcher in the middle. Section 5.4 describes a three-level chain, so
detection that assumes it will attach to the wrong process in both titles.

### A-4 holds: stages hold their own sockets

| Stage | Process | Flows | Bytes | Ports |
| --- | --- | --- | --- | --- |
| ESO platform | `steam.exe` | 5 | 180,904 | 443, 27036 |
| ESO shim | `zosSteamStarter.exe` | 0 | 0 | none |
| ESO launcher | `Bethesda.net_Launcher.exe` | 16 | 198,118 | 443 |
| ESO client | `eso64.exe` | 4 | 3,426,000 | 24120-24131 |
| DIV2 platform | `steam.exe` | 5 | 55,795 | 443, 80, 27036 |
| DIV2 shim A | `TheDivision2.exe` (19712) | 0 | 0 | none |
| DIV2 shim | `UbisoftGameLauncher.exe` | 0 | 0 | none |
| DIV2 service | `upc.exe` | 10 | 1,774,959 | 443 |
| DIV2 shim B | `TheDivision2.exe` (7476) | 0 | 0 | none |
| DIV2 anti-cheat | `EACLaunch.exe` | 0 | 0 | none |
| DIV2 client | `TheDivision2.exe` (47156) | 31 | 13,099,810 | 13000, 22003, 51000, 55002, 443 |

Role separation is clean. Each stage holds its own sockets on its own port
ranges, no handle is shared, and the roles in section 15.2 map onto real
processes without ambiguity.

`EACLaunch.exe` holds no sockets, so the anti-cheat launcher performs no
network activity fragcap would need to classify.

### Three processes share one image name

**Div2 runs three distinct processes named `TheDivision2.exe`, and only the
third holds any sockets.** The first is a Steam shim, the second is spawned by
the Ubisoft launcher, the third is spawned by `EACLaunch.exe` and is the actual
client.

A profile matching on image name alone matches all three. Two of them carry no
traffic, so a matcher taking the first hit attaches to a process that never
transmits and reports an empty capture as success.

**Consequence: stage match rules need ancestry, not just an image name.** A
rule must express "image is `TheDivision2.exe` AND it descends from the stage
matching `EACLaunch.exe`".

The schema already supports this. Section 10.3 defines a `descends_from`
predicate resolving against the synthetic process tree, so no new predicate is
needed, and an earlier reading of this finding as a schema change was wrong.

What was missing is enforcement. Nothing required a profile author to use
ancestry, and the failure when they do not is silent: the stage binds to a
process that never transmits, and the session completes reporting success over
an empty capture. Section 15.4 now makes ambiguous image matching a validation
error, with a runtime warning for the case a profile cannot know about in
advance. That lands before S05.

## Q-5: the handoff is not on loopback (A-5 FAILS)

**There is no loopback conversation between the launcher and the client in
either title.** Verified by attributing every loopback conversation to an
owning process:

- The largest loopback conversation, 5,415,000 bytes on ports 55524 and 55523,
  has `eso64.exe` (pid 48672) on **both** ends. It is intra-process IPC.
- `Bethesda.net_Launcher.exe` likewise talks only to itself on loopback.
- No conversation exists with the launcher on one end and the client on the
  other.

**The mechanism for ESO is not established.** `eso64.exe` is launched with:

```text
eso64.exe ... Language.2=en viewer_id=false onetime_token=false
          {ProductID} is_steam=true
```

Both candidate parameters are the literal string `false`, and `{ProductID}` is
an unsubstituted template placeholder. That reads as an unused argument
template at least as readily as a disabled handoff channel. Tracked as Q-10.

**For Div2 the mechanism is a named pipe**, observed directly.
`UplayService.exe` receives `\\.\pipe\terminal_1_uplay_service_ipc_pipe_`,
base64 encoded, on its command line. Section 6.2's A-5 fallback anticipated
exactly this, so the fallback applies as written rather than needing amendment.

### What follows

Section 6.2's A-5 fallback says a handoff over named pipes or shared memory is
out of scope for a network capture tool and should be documented as such. A
command line argument is a third mechanism, equally invisible to packet
capture, and the same conclusion applies to what the capture can show.

**But fragcap can observe it anyway, through a component it already has.** The
process watcher in section 10 reads command lines when it builds the tree. The
handoff is therefore observable, just not as a packet. Getting started
documentation should say plainly that the handoff appears in process metadata
rather than in the capture, so users do not go looking for a packet that does
not exist.

Loopback capture is still required, for the reason in section 12.2: both
titles use loopback heavily for intra-process IPC, and ESO moved 5.4 MB of it
in twenty minutes. Excluding loopback would leave a visible gap.

### A privacy hazard this exposes

**Correction.** An earlier revision of this document claimed a live session
token appears on `eso64.exe`'s command line, and called it the documented
handoff mechanism. That was inference from a parameter name. It was not
documented, and it was not supported by the capture.

An entropy scan over all 3,694 command lines from both sessions was run to
test it. **No credential was found in either title.** The highest-entropy
arguments decode to file paths, the Uplay named pipe path, Rust build
identifiers, and unrelated tooling identifiers from concurrent work. The
claim is withdrawn and tracked as the open question Q-11.

**What the scan did establish** is smaller but real: every command line
contains the operator's Windows account name inside user-profile paths, along
with installation layout and whatever unrelated software was running. That is
identifying, it is present in every process record, and fragcap's process
watcher would capture it by default.

That is sufficient on its own for the rules below, and it is what they are
scoped to. Protection against credentials is a precaution against a known
category, not a response to something observed here.

Recommended, before S11 implements the process watcher:

- Command lines are **not** captured by default. A flag enables them.
- When captured, user-profile path segments are masked, since the account name
  is the identifying element and it is present in nearly every argument list.
- Parameters named for credentials are redacted as a precaution against the
  category. `onetime_token` is deliberately **not** on the shipped list: no
  evidence supports treating it as one, and seeding a redaction list from a
  withdrawn claim would preserve the error in a place nobody rereads.
- Command lines never enter `.fcapng` annotations or JSON Lines output
  regardless of the flag. They belong in diagnostics only.
- Name-based redaction only catches parameters someone thought to name. An
  entropy check over argument values is the stronger complement, and is what
  actually settled this question.

## Q-1: attribution holds

| Session | Frame-weighted | UDP conversation misses | Bytes in those misses |
| --- | --- | --- | --- |
| ESO | 99.45% | see below | 0.0935% of UDP bytes |
| DIV2 | 98.78% | see below | comparable |

Every substantial flow attributed, including all gameplay. The conversations
that miss are ephemeral DNS sockets that open and close inside one poll
interval and carry a negligible share of bytes.

**A-1 holds.** Read the byte share rather than the conversation count: the
count is dominated by DNS lookups and foreign LAN multicast, neither of which
says anything about whether gameplay is attributable.

The earlier concern that PF-3 (no remote endpoint in the UDP socket table)
threatened attribution did not materialize. ESO gameplay is **entirely TCP**,
so the full 5-tuple is available. Div2 gameplay UDP rides a single long-lived
socket, so the local endpoint alone identifies it. `FlowKey` still needs the
asymmetric join, but the impact is smaller than feared.

## Q-2: not relay tunneled (A-3 holds)

ESO gameplay goes to `198.20.200.0/24`, ZeniMax-operated address space, on
TCP ports 24120 to 24131, connected to by address with no DNS lookup. Four
concurrent connections, longest 586 seconds.

Div2 gameplay goes to `20.110.39.23`, Microsoft Azure, on TCP 13000 and UDP
22003 simultaneously, both about 766 seconds, plus `35.195.178.186:55000`
(Google Cloud).

Neither is relayed. Div2 runs publisher infrastructure on third-party cloud,
which is ordinary hosting rather than a relay: traffic goes directly to the
game server, and no intermediary re-originates it.

Gameplay endpoints are reached **by address, without a DNS lookup**, which
means hostname-based identification will not find them. Address-range and
port-range matching is required.

## Q-3: connection lifetimes (A-2 holds)

| Session | Closed connections | Shorter than the 250 ms poll | Frames on those |
| --- | --- | --- | --- |
| ESO | 11,246 | 0 | 0% |
| DIV2 | 1,003 | 0 | 0% |

**Not one connection closed inside a poll interval.** Gameplay connections run
for hundreds of seconds. Polling at 250 ms is comfortably sufficient, and PF-4
showed the direct socket table call costs 1 to 3 milliseconds, so a tighter
cadence is available if a title ever needs it.

Event-driven socket tracking (section 28) is not justified by this evidence.

## Q-6: encryption posture

| Session | TCP payload | UDP payload |
| --- | --- | --- |
| ESO | 7.61 bits/byte | 7.951 bits/byte |
| DIV2 | 7.862 bits/byte | 7.947 bits/byte |

Everything above the 7.5 threshold: encrypted or compressed throughout. 22 and
25 distinct TLS server names observed respectively.

Users get timing, sizing, endpoints, and attribution. They do not get readable
game packets. Section 19.6 already says this and it is confirmed.

## Capture environment notes

**Docker dominated the earlier sessions.** `com.docker.backend.exe` (pid 4680)
carried 428 MB and 680 MB of UDP to `66.56.80.181:8080`, up to 94% of total
bytes, unrelated to either game. Present in every capture including a control
run with no game. Worth stopping before a capture, and a concrete argument for
the dynamic filter tightening in section 12.2.

**Concurrent development work appears in captures.** A Rust test suite and its
PostgreSQL instance on port 5433 produced thousands of loopback conversations
in the ESO session. A capture taken on a working machine is noisy, which is an
argument for role filtering being available early rather than late.
