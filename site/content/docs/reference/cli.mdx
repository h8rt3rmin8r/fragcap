<Callout title="Why it matters here">
Every command that captures needs the **npcap** driver installed in
WinPcap-compatible mode. Run `fragcap doctor` first; it reports the driver's
presence without capturing anything.
</Callout>

fragcap has one binary and a small set of commands, grouped into Capture, Targets,
Environment, and Data. This page lists what each one does and the flags it accepts.
The binary's own `--help` is authoritative and is generated from the same
definitions; this page is the readable version. Running `fragcap` with no command
lists your registered targets and points at `--help`.

## Global options

These apply to every command:

| Flag | Effect |
| --- | --- |
| `--quiet` | Suppress progress; keep warnings and errors. |
| `--silent` | Suppress everything except errors. |
| `--json` | Emit machine-readable structured output instead of human text. |

## Capture

### `capture`

Capture a target's traffic. This is the primary command. Name the target one of
three ways, exactly one of which is required:

```text
fragcap capture 1 --out capture.fcapng
fragcap capture --target the_elder_scrolls_online --out capture.fcapng
fragcap capture --process eso64.exe --out capture.fcapng
```

| Flag | Meaning |
| --- | --- |
| `--target <SELECTOR>` | A stored target: an exact handle, a case-insensitive exact name, or a 1-based row index from the `targets` listing. A bare number given here is a row index. |
| `--id <N>` | Select a stored target by its durable stable identifier (the machine-facing form automation uses). |
| `--process <NAME>` | Capture a running process by image name, with no stored target. |
| `--path <SUBSTR>` | A case-insensitive substring the target's full image path must contain (disambiguates a shared image name). |
| `--path-regex <RE>` | A regular expression the target's full image path must match. |
| `-o, --out <PATH>` | The output capture file (pcapng). Shorthand for a file sink. |
| `--mode <MODE>` | Capture mode: `file`, `stream`, or `ring`. Defaults to `file`. |
| `--sink <SPEC>` | An output sink, repeatable: `file:PATH`, `jsonl:PATH`, `pipe:NAME`, or `tcp://HOST:PORT`. |
| `-d, --duration <DUR>` | The capture duration bound, measured from arm. |
| `--wait <DUR>` | How long to wait for the target before giving up (the acquisition timeout). |
| `--max-packets <N>` | Stop after this many captured packets. |
| `--max-bytes <SIZE>` | Stop after this many captured bytes (integer plus `b`/`kb`/`mb`/`gb`). |
| `--roles <A,B>` | The roles to capture, comma-separated. Scopes which stages trigger (enforced). |
| `--direction <DIR>` | The flow direction to scope to: `in`, `out`, or `both`. Recorded but not yet enforced (see below). |
| `-i, --interface <NAME>` | A capture interface, repeatable. |
| `--loopback` | Include the loopback adapter. |
| `--no-payload` | Write metadata only, no packet payloads. |
| `--ring <WINDOW>` | The ring window, for `--mode ring` (a duration or a size). |
| `--launch` | Start the target through its platform launcher, then capture it (Windows only). The target must be Steam anchored; register one with `targets add --steam <app_id>`. This is a property of the stored target, not a value passed to `--target`, which never accepts an app id. |
| `--catalog-db <PATH>` | Override the catalog store consulted while resolving a `--target`. |
| `--local-db <PATH>` | Override the local store where `--target` selectors resolve. |

Durations accept the same grammar throughout: an integer and a unit, such as
`30s`, `5m`, or `2h`. See [capture modes](/docs/guides/capture-modes) for what
`--mode` and `--ring` do. A non-file sink (`pipe:`, `tcp://`) has no extension to
infer a format from, so it names one explicitly with `,format=pcapng` or
`,format=jsonl`.

<Callout title="Directional filtering is not yet enforced">
`--direction in` or `--direction out` is recorded on the effective configuration
and reported, and fragcap warns that directional output filtering is deferred: a
non-default direction does not currently scope the captured packets, so the
output still contains both directions. `--roles` scoping, by contrast, is
enforced.
</Callout>

### `deep-capture`

Run Capture together with explicit, target-scoped local proxy inspection. The
first implementation requires a stored target, `--launch`, explicit CA trust
confirmation, an installed `mitmdump` backend, and current facts proving the
supported cold Steam protocol launch path.

```text
fragcap deep-capture sample-target --launch --trust-ca --har --key-log
```

`--bundle <DIR>` selects the session bundle directory. The ordinary duration,
wait, packet, byte, interface, and payload controls remain available. `--har`
writes an HTTP-oriented projection when HTTP semantics are observable, while
`--key-log` creates a proxy-owned TLS key log at its final bundle path before
traffic starts so Wireshark can consume it during the session.

Deep Capture refuses unknown or unsupported launch paths before starting the
proxy or changing trust. See [Deep Capture compatibility]
(/docs/reference/deep-capture-compatibility) for current traffic support,
certificate-pinning and QUIC limits, and the local evidence matrix.

### `replay`

Play a capture file back. Not yet implemented; the command parses and reports that
it is unavailable rather than the parser rejecting it.

## Targets

Capture targets live in your local store (`local.db`). fragcap discovers installed
titles and registers them for you; you can also register, inspect, and remove them
by hand.

### `targets`

With no subcommand, `fragcap targets` runs discovery, registers any newly found
titles, and prints the numbered listing (the row numbers are what `fragcap capture
<n>` honors). See [Getting started](/docs/getting-started#3-find-a-target).

- `fragcap targets add [NAME] --db <local.db>` registers a target and derives a
  unique handle. `--steam <APP_ID>` registers an installed Steam title (anchored to
  `steam:<APP_ID>`, taking its name from the installation); `--anchor <PLATFORM:ID>`
  gives a deterministic identity (mutually exclusive with `--steam`); `--exe <NAME>`
  names a launch executable; `--handle <OVERRIDE>` overrides the derived handle; and
  `--socket-holder yes|no|unsure` is the non-interactive form of the "which process
  holds the sockets" question (requires `--exe`). A `no` or `unsure` answer leaves
  the target's client unresolved (it reads `needs a target`); capturing it anyway
  runs in launch-and-observe mode, and when the run sees the real socket holder the
  target is promoted to that client, after which it reads `ready`.
- `fragcap targets list --db <local.db>` lists registered targets with their row
  index, handle, and identifier.
- `fragcap targets show <SELECTOR> --db <local.db>` (or `--id <N>`) shows how one
  target resolves and lists its local Deep Capture compatibility evidence. The
  view is read-only and reports unknown rather than inferring support when no
  facts exist.
- `fragcap targets remove <SELECTOR> --db <local.db>` (or `--id <N>`) removes one
  target; an ambiguous name lists its matches and refuses.
- `fragcap targets export [SELECTOR] --db <local.db>` writes registered targets as
  a JSON array to standard output; `fragcap targets import <FILE> --db <local.db>`
  merges a target-entry array back in on the stable identifier.
- `fragcap targets discover --catalog-db <catalog.db> --local-db <local.db>
  [--steam-root <PATH>]` walks Steam and the known install roots and lists the
  candidates found (reads only).
- `fragcap targets scan <DIR> [--catalog-db <catalog.db>] [--db <local.db>]` treats
  one directory as a single candidate; with `--catalog-db` it detects the engine,
  anti-cheat, and DRM technologies present and carries them as evidence; with
  `--db` it registers what it finds.

### `technologies`

Detect the technologies present in a game's install directory (engine, anti-cheat,
and DRM), from the catalog's signature table.

```text
fragcap technologies --path "C:\Games\MyGame" --catalog-db catalog.db
```

### `steam`

Steam-specific inspection. `fragcap steam list` enumerates the installed Steam
titles this machine can see. Registering a Steam title as a capture target is
`fragcap targets add --steam <APP_ID>`, not a `steam` subcommand.

## Environment

### `doctor`

Report environment readiness: identity, platform, the capture driver, tracing,
interfaces, and the Wireshark integration. It captures nothing.

```text
fragcap doctor
```

`fragcap doctor --fix` adds an interactive action layer above the same report: it
offers to perform the remediations the report named, one at a time, under your
confirmation (for example relaunching elevated, registering the extcap integration,
fetching the catalog, or, in a network-capable build, fetching and launching
npcap's own signed installer). It acts only on remediations the plain report
already printed and never installs anything without asking. `--yes` pre-confirms
every offered action for unattended interactive use. `--fix` is refused with
`--json`, and when stdout (or, without `--yes`, stdin) is not an interactive
terminal.

The Deep Capture section reads local CA trust without changing it. On Windows it
matches only exact SHA-1 thumbprints previously recorded by fragcap session
manifests, then checks current-user Root (the supported scope) and local-machine
Root (an unexpected broader scope). It does not identify ownership from certificate
names. The report distinguishes absent, supported, wrong-store, mismatched, and
unobservable states and prints observed thumbprints identically in human and JSON
output. Wrong-store or mismatched trust offers confirmation-gated cleanup only
when the exact manifest-backed thumbprint and store can be named. Deep Capture CA
warnings do not block passive Capture readiness.

### `extcap`

Analyzer integration. Wireshark and compatible analyzers invoke `fragcap` as an
extcap capture source; you do not normally run the protocol form by hand. It
presents one `fragcap` interface whose capture dialog selects a stored **target**
and mirrors `capture`'s options (`--target`, `--roles`, `--direction`,
`--loopback`), so the analyzer dialog and the command line select capture
identically: you pick a registered target (by handle, name, or row index) in the
dialog exactly as you would pass `--target` to `capture`. The other part you use
directly is registration, below.

#### `extcap install` / `extcap uninstall`

Register or unregister fragcap as a Wireshark extcap source, so Wireshark lists it
in its capture interfaces.

```text
fragcap extcap install            # register for the current user (the default; idempotent)
fragcap extcap uninstall          # unregister (idempotent; a no-op if not registered)
fragcap extcap install --system   # register machine-wide, for every user
fragcap extcap install --dir DIR  # register into an explicit directory
```

The scope selectors `--user`, `--system`, and `--dir` are mutually exclusive; with
none given, the default is the current user. The per-user form copies the running
fragcap binary into your own Wireshark extcap directory and needs no elevation. On a
shared computer, **each user who wants the Wireshark integration runs `fragcap
extcap install` once.** If Wireshark does not show fragcap as a capture source, run
`fragcap doctor`, which reports whether the integration is registered for you and
prints the exact command to fix it. To register for every user, an administrator
runs the machine-wide form (writing into Wireshark's system extcap directory needs
the privilege to write there).

The Windows installer (`.msi`) can also register the integration for you, for the
current user or machine-wide, through its optional Wireshark integration step (both
choices off by default). Both are exposed as installer properties
(`REGISTEREXTCAP_USER`, `REGISTEREXTCAP_MACHINE`) for a silent install.

## Data

### `catalog`

Maintain the disposable catalog store (`catalog.db`).

`--db` is an override, never a requirement: with none, every command below
resolves the store fragcap manages, through `FRAGCAP_CATALOG_DB` if set and the
per-user default otherwise, creating it on first use.

- `fragcap catalog import <SEED>` loads a local JSON seed document.
- `fragcap catalog export` exports the store to schema-conformant JSON on
  standard output.
- `fragcap catalog seed` fills the store. With no `--tier` it fills every tier
  that has a source available and names every tier it skipped, with the reason.
  `--tier catalog|launch|engine|signature` selects one, and is repeatable.
- `fragcap catalog seed --tier signature` fills the detection signature table
  from a bundled document, so `technologies` and discovery detect engines,
  anti-cheat, and DRM from the store. Offline and idempotent; the released
  `catalog.db` already ships with it done.
- `fragcap catalog seed --tier engine --from <doc>` seeds one tier from a local
  document. `--from` requires exactly one `--tier`: the offline documents are
  bare JSON arrays that do not say which tier they are, and guessing would write
  the wrong columns silently, so an ambiguous invocation is refused. A
  network-capable build adds the live `--steam` and `--pcgamingwiki` sources.

### `schema`

Validate JSON artifacts against the master schema, or print it.

- `fragcap schema validate <FILE>` reports every structural violation in one pass.
  See [the target schema](/docs/reference/target-schema).
- `fragcap schema print` writes the embedded master schema to standard output.
