# Phase 0 Research: launch-data accumulation

## Decision 1: source of launch data

**Decision**: Read the user's own local `appcache/appinfo.vdf` with a
hand-rolled binary parser. No network, no new dependency.

**Rationale**: The launch configuration (executable, arguments, type, oslist,
osarch, betakey) lives only in Steam's PICS app-info. Locally, Steam caches it in
`appinfo.vdf`, keyed by app id, with a per-app change-number. Reading that file
needs no Steam session, no credential, and no capture driver. It is the same
class of local metadata read the crate already does for `libraryfolders.vdf` and
the `.acf` manifests, and it is P-1 clean by construction.

**Alternatives considered**:

- **A SteamKit-class Rust crate (network PICS)**, for example `steam-vent`.
  Rejected. It reaches the whole catalog, but it pulls a large asynchronous,
  protobuf, and cryptographic graph. That is the "no gratuitous graph" test that
  rejected `ureq` (42 ICU4X crates) and `boon` in prior slices, and it would
  require a fresh crate-by-crate license audit with a real risk of a
  CDLA-Permissive transitive (the `webpki-roots` trap S035 hit). It also leaks
  nothing the local read leaks, so it buys catalog scale the privacy-driven
  design deliberately does not want.
- **A `steamcmd` subprocess** (`+app_info_print`, scrape stdout). Rejected on
  P-7: a wrapper that parses a subprocess's output is exactly the missing-Rust-
  capability signal the constitution forbids. It is also throttled and format-
  unstable.
- **The store's shipped data (maintainer-seeded Tier 2)**. Rejected on privacy:
  baking the maintainer's local launch data into the shipped database would leak
  which games the maintainer owns. This is the whole reason the maintainer-run
  Tier 2 seeder was cancelled and replaced by per-user local accumulation
  (community pooling is deferred to issue #94).

## Decision 2: the binary appinfo.vdf format

**Decision**: Parse the documented binary layout by hand, framing each app
section by its size field so a bad section is isolated and the walk resyncs.
Support the format versions Steam has written in practice (magic `0x07564427`,
`0x07564428`, `0x07564429`).

**Format** (little-endian throughout):

File header:

- `magic`: u32. Known: `0x07564427` (v27), `0x07564428` (v28), `0x07564429`
  (v29). Anything else is an unrecognized-format error (not a silent empty read).
- `universe`: u32.
- v29 only: `string_table_offset`: i64. In v29 the key of each binary key-values
  node is a u32 index into a string table stored at this offset (a u32 count
  followed by that many NUL-terminated strings), rather than an inline
  NUL-terminated key. v27/v28 use inline keys.

Then a sequence of app sections until a terminating `appid` of `0x00000000`:

- `appid`: u32 (0 terminates the list).
- `size`: u32. Byte length of the rest of this section, from just after this
  field to the end of the section's key-values blob. **Used as the frame**: read
  exactly `size` bytes, parse within them, and on any inner fault count the app
  failed and advance to the next section by this length (FR-008 resync).
- `info_state`: u32.
- `last_updated`: u32.
- `pics_token`: u64.
- `text_vdf_sha1`: 20 bytes.
- `change_number`: u32. **This is the staleness key** recorded in the store
  (FR-011a).
- v28 and v29 only: `binary_vdf_sha1`: 20 bytes.
- the binary key-values blob: a tree of typed nodes. Node type byte prefixes:
  `0x00` nested object (key, then children, terminated by `0x08`), `0x01` string
  (key, NUL-terminated value), `0x02` int32 (key, 4 bytes), `0x07` uint64 (key, 8
  bytes), and the terminator `0x08`. Other numeric types (`0x03` float32, `0x06`
  color/int, `0x0A` int64) are read for their fixed width and ignored; an
  unknown type byte is a section parse fault (counted, resynced).

**Launch extraction**: parse each section's blob into the existing
`vdf::VdfValue` tree, then navigate `config -> launch -> <index> -> { executable,
arguments, type, description, config -> { oslist, osarch, betakey } }`. Each
index becomes one launch entry, stored verbatim (FR-005). An entry with no
`executable` yields nothing to store (an executable is the one required field).

**Rationale**: Reusing `VdfValue` means the binary parser produces the same tree
shape the text parser already produces, so the navigation and the tests read the
same way. The size-framing gives per-app failure isolation for free, which maps
directly onto the P-4 conservation requirement.

**Honest limitation (recorded, mirrors S09 live capture)**: A hand-transcribed
binary layout can be self-consistent with a synthetic fixture yet wrong against a
real file, the same P-9 offset trap S09 noted for the pcap header. The parser is
therefore validated offline against generated bytes (self-consistent), and
validation against a real `appinfo.vdf` on a machine with Steam installed is a
manual step the operator runs, exactly like Tier-2 live capture. The size-framing
limits the blast radius: a drifted inner parse fails its one section and is
counted, rather than corrupting the whole file's read. The parser reads only the
fields it needs and skips the rest by width, so unknown or reordered sibling keys
in a real file do not derail it.

**Alternatives considered**: Committing a real multi-megabyte `appinfo.vdf`
fixture. Rejected: large, contains Valve data, and drifts. A small synthetic
generator (the pcap-corpus precedent) is readable, controlled, and drift-proof.

## Decision 3: staleness by change-number, and where it is stored

**Decision**: Record each app's appinfo `change_number` in a new nullable
`appinfo_change_number` column on `games`, added by the store's first
schema-version migration (v1 to v2). An app is refreshed only when the cache's
change-number is strictly greater than the stored one; equal means skip.

**Rationale**: The operator chose change-number staleness over a plain
has-it-or-not check so an app is re-read only when Steam actually updated it. The
store has no such column today, so a migration is required. It is additive and
store-internal: `ALTER TABLE games ADD COLUMN appinfo_change_number INTEGER` for
an existing v1 store, and the column is present in the fresh-store DDL. The value
is bookkeeping, never exported, so the export projection and the published schema
are untouched and the "store cannot hold an unexportable row" invariant is
unaffected.

**Alternatives considered**:

- **Have-it-or-not staleness** (no migration). Rejected: contradicts the
  operator's explicit change-number default and would never refresh a game whose
  launch config Steam changed after it was first learned.
- **A separate side table keyed by appid**. Rejected: a nullable column on the
  existing row is simpler and the value is one-per-game, exactly the row's grain.

## Decision 4: what accumulation does not write

**Decision**: Write launch entries and the change-number only.
`launcher_mediated` and `token_required` are left exactly as they were.

**Rationale**: The cache has no reliable field for either. `launcher_mediated`
would be a heuristic (P-9 forbids guessing it from this source), and
`token_required` has no source at all and is not exportable. Both are out of
scope; a later slice may derive `launcher_mediated` as an explicit judgment.

## Decision 5: where the orchestration lives and when it runs

**Decision**: The orchestrator lives in the `fragcap` facade behind the `targets`
feature and owns the reconciled account. The CLI's `run.rs` calls it at capture
start, only when a hint database is configured (the same `--hint-db` /
`FRAGCAP_HINT_DB` the resolver already uses), writing to that same store. With no
hint database configured there is no accumulation, matching today.

**Rationale**: The account spans both siblings (the installed set and parse
outcomes from `fragcap-steam`, the stored change-numbers and merges from
`fragcap-targets`), so the facade is the only crate that can compute it honestly,
and the sibling rule forbids either backend crate from driving the other. This is
the S07/S08 precedent: the end-to-end composition and its test live in the
facade. Running at capture start (not a separate command) is the operator
default; a progress line keeps a slow first run legible (FR-010).

**Alternatives considered**: A `LaunchSource` trait plus `FixtureLaunchSource` in
`fragcap-targets`, mirroring `CatalogSource`/`EngineFeed`. Rejected as
unnecessary indirection here: unlike the network seeders, this source is a local
file that `fragcap-steam` already parses offline, so the facade orchestrator is
directly offline-testable without a trait seam, and the account genuinely belongs
in the facade rather than in a targets-side seeder.
